# 編輯客服知識庫

`data/knowledge.md` 不是一般文件——它整份會被塞進 AI 的 system prompt（`getKnowledge()`，`src/server.js:89`），直接決定機器人對真實客戶說什麼。改壞了不會有錯誤訊息，只會讓客服回答開始失準。

這是**長照機構**的對外客服。回答涉及補助資格、名額、費用、個案照護的內容有法規與信任風險，不是文案問題。

## 動手前

先讀整份 `data/knowledge.md`。它有既定結構（回覆原則 → 基本資料 → 聯絡方式與營業時間 → 交通與停車 → 各項服務），新內容要放進對的區塊，不要在檔尾另起爐灶。

## 不可以動的東西

檔案開頭的 `## 回覆原則` 和 `### 資料庫外問題處理方式` 是行為護欄，不是可有可無的前言。它們明確規定了機器人**不准**自行承諾名額、補助資格、報名成功、價格優惠或醫療照護結果，以及什麼情況要請客戶來電。

除非使用者**明講**要改這些原則，否則不要碰。如果新增的內容會跟這些原則衝突（例如寫了一個看起來像保證的句子），停下來指出衝突，不要默默兩邊都留著。

## 事實類內容的規則

**不要自己編。** 電話、地址、字號、營業時間、費用、負責人姓名——這些只能來自使用者提供，或檔案裡已經有的。查不到就問，不要從公司名稱推測，也不要用「一般長照機構通常是……」補空白。

寫入時沿用現有格式：

- 電話一律寫 `02-2912-1860` 這個格式，全檔一致
- 營業時間逐日列，維持 `週一：08:00-12:00、13:00-17:00。` 的寫法
- 地點、交通、停車類的內容附 Google Maps 連結（既有慣例）
- 每個項目用 `- ` 開頭，句尾加句號，跟現有行一致

## 不確定的資訊怎麼寫

知識庫本身的原則是「資料不足或可能變動 → 請客戶來電確認」。新增內容時延續這個處理方式：與其寫一個可能過期的細節，不如寫成「請來電 02-2912-1860 確認」。

特別是名額、補助資格、費用、申請流程——這些會變，而且答錯的代價是真實的客訴。

## 改完之後

1. 回報你改了哪幾個區塊，用 diff 呈現，不要只說「已更新」
2. 如果動到營業時間、電話、地址這類高頻問答的事實，提醒使用者這會立刻影響線上客服回答
3. 不需要重啟服務——`getKnowledge()` 每次請求都重讀檔案，但 Render 上要等這次 commit 部署完才會生效

## 這個檔案不放什麼

API 金鑰、內部流程、員工個資、個案資料。整份檔案會進 AI 的 prompt，等於可能出現在對客戶的回覆裡。
